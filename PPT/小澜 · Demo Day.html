FDE Demo Day · 电商赛道 · 12 min

一家懂 30-50 岁用户的公司，
怎么懂 18-30 岁的人？

小澜 —— 一个可以被鞭打的老板数字分身

澄野商业 × 澜序 LANSU

向 CEO 汇报高佳慧 · 邵俊钦 · 梁曦霖
#人群洞察 #证据链 #Agent

一家在 30 到 50 岁用户身上做了五年的内衣公司，刚接了一个面向 18 到 30 岁年轻人的新品牌。他们最大的焦虑不是投流——是他们根本不了解这群年轻人。我们做的事叫"小澜"——一个可以被鞭打的老板数字分身。它做的事就一件：让你说的每一句"我觉得"，都能点回原表哪一行。

01 · 我们看到问题

不是缺数据，
是现有方法没法把信息变成判断

01
经验型判断无法验证

开会时有人说"我刷抖音感觉年轻人喜欢这样"，另一个人说"我觉得不是"。讨论到此结束——没有证据，谁声音大谁赢。

02
散落数据串不起来

M1 说退款 47%，M2 说年轻人曝光只占 15.5%，M3 说尺码问题最多——但三件事分散在不同部门的表格里，口径还不统一。没人把它们放在一起看。

03
没有反馈机制

今天做的判断——"年轻人应该喜欢这个款式"——对了还是错了？三个月后没人回头验证。下一次开会还是靠感觉。

CEO 直接给了我们三种死法：不能只画画像 / 不能做聊天机器人 / 不能增加录入负担

目前营销团队怎么工作的？靠个人经验、平台后台截图、人工刷内容、零散会议。三个问题：第一，经验型判断无法验证——开会靠"我刷抖音感觉"。第二，散落数据串不起来——M1说退款高、M2说年轻人少、M3说尺码问题多，但没人把三件事放一起看。第三，没有反馈机制——今天做的判断对了错了，三个月后没人回头验证。CEO在题目里直接给了我们三种死法——不能只画漂亮的用户画像、不能做上传文件吐总结的聊天机器人、不能增加录入负担。

02 · 三个事实

数据里已经写着答案，
只是没人把它们串起来

01
触达错配 · M2 · F 事实

24 场直播，18-30 岁仅占曝光 15.5%，18-24 岁 TGI 0.27（最低 0.17）。TGI 是人群偏好指数，1.0 是平均水平——0.27 就是严重偏低。整条流量链路朝成熟人群倾斜。

02
直播高退款源于期待错位 · M1-05 + M3 · I 推断

6 月退款金额率 47%，直播占退款 68%。客服原声："视频双肩带、链接单肩带""有点凸点""穿身上闷"——期待错位写在原话里。M3 是人工样本不是全量，所以标 I。

03
专家最担心 AI 胡说 · M5 · H 假设

五位内部专家几乎全部关注 AI 可靠性——他们也互相冲突。这条直接决定了我们的架构：校验层不是可选项，是必选项。专家观点进假设库，不进规则层。

F=事实 · I=推断 · H=假设 —— 每个数字都标了证据等级，这是和"刷抖音感觉"的区别

我们把 M1 到 M5 花四小时全读了一遍。三个事实。每条都标了来源和证据等级——F是事实、I是推断、H是假设。柯洲老师说好答案=好提问+好上文+好模型——我们把上文喂饱了。事实一：触达错配，来源M2，这是事实。事实二：退款47%、直播占68%、客服原声印证期待错位——来源M1-05加M3，推断，因为M3是人工样本不是全量。事实三：M5五位专家担心AI胡说——这是假设，专家也互相冲突。这条直接决定了架构——校验层不选可选项。

先说清楚用了什么AI：DeepSeek选题和措辞，代码算数。LLM永远看不到原始数据行，只看到已经算好的聚合结果。为什么？M5五位专家都怕AI胡说——所以我们让代码拦截AI的幻觉。Edward你开始。拖M2人群画像表、别拖M1直播明细。用跨表问题——比单表快，横跨M1+M2。点开证据看原表行列。抽鞭子真的改thinking参数。深度~28次工具调用，快速腰斩。用户自己决定要深度还是要速度。

货不对板，
不是货不行。

🟡 中置信度

退款金额率 47% · 直播占退款 68%
商品+尺码占工单 66.8% · 仓库工单仅 11% 环比无变化
客服原声："和图片不一样""杯型不合适""穿身上闷"

⚠️ 硬边界

0.82% 工单关联率 ≠ 退款责任率
M4 商品行粒度 ≠ 订单数——统计强制走 COUNT DISTINCT 主订单号
缺关键数据：退款订单 × 原因 × SKU 交叉关联

👤 人判断什么

功能性缺陷 → 改产品。尺码认知偏差 → 改详情页。

数据能帮你定位到"尺码问题是大头"，具体动哪个、怎么动——得你来判断。

邵俊钦。第二条洞察。退货的根因基本锁定了——货不对板，不是货不行。用户拿到手之后发现和预期不一致。仓库端工单只占11%，环比没变化——发货环节不是退款压力的源头。中置信度——三个来源方向一致但客服文本是人工抽样的。硬边界：0.82%工单关联率不等于退款责任率，M4商品行不等于订单数我们用COUNT DISTINCT主订单号。缺关键数据：退款订单乘原因乘SKU的交叉关联还没跑出来。人判断：功能缺陷改产品，尺码偏差改详情页。数据能定位到尺码问题是大头，具体怎么动你决定。

07 · 架构 · 梁曦霖

AI 原生架构：宁可少说，不可错说

M1-M5 预置 → DuckDB 证据库
28 指标 + metrics.yaml → Agent 5 工具
≤3 轮 · 只见摘要和聚合 → validator 四条校验
不过就丢弃 → 观点卡
用户拖入文件 → parse_excel 即时解析 → 会话临时库（LLM 不碰原始行）

三道硬约束

① 数字由代码算，LLM 不碰计算器
② LLM 只见摘要和聚合，不见原始行
③ 无证据不输出——ID 不存在就丢弃

五种降级

API 挂 → 模板卡片
表缺失 → 不生成 + 列缺什么
全被丢 → 原始异常列表
超范围 → "当前数据无法回答"
链路崩 → "系统出错，再试一次"

AI 原生，不是边缘贴皮

AI 进核心分析链路
——选题和归因
不是客服，不是文案
数据流围绕 AI 能力边界重切
边缘型短期没事，长期附庸

梁曦霖讲架构。看这条数据流：M1到M5预置加用户拖入 → DuckDB证据库28个指标 → Agent 5个工具 ≤3轮，LLM只看到摘要和聚合 → validator四条校验硬拦截 → 观点卡。三道硬约束：代码算数LLM不碰计算器、LLM不碰原始行、无证据不输出。五种降级全跑通——宁可少说不可错说。右下角：这是AI原生做法——AI进核心分析链路，不是给旧流程加聊天插件。

07 · 架构 · 梁曦霖

AI 原生架构：宁可少说，不可错说

M1-M5 预置 → DuckDB 证据库
28 指标 + metrics.yaml → Agent 5 工具
≤3 轮 · 只见摘要和聚合 → validator 四条校验
不过就丢弃 → 观点卡
用户拖入文件 → parse_excel 即时解析 → 会话临时库（LLM 不碰原始行）

三道硬约束

① 数字由代码算，LLM 不碰计算器
② LLM 只见摘要和聚合，不见原始行
③ 无证据不输出——ID 不存在就丢弃

五种降级

API 挂 → 模板卡片
表缺失 → 不生成 + 列缺什么
全被丢 → 原始异常列表
超范围 → "当前数据无法回答"
链路崩 → "系统出错，再试一次"

AI 原生，不是边缘贴皮

AI 进核心分析链路
——选题和归因
不是客服，不是文案
数据流围绕 AI 能力边界重切
边缘型短期没事，长期附庸

梁曦霖讲架构。看这条数据流：M1到M5预置加用户拖入 → DuckDB证据库28个指标 → Agent 5个工具 ≤3轮，LLM只看到摘要和聚合 → validator四条校验硬拦截 → 观点卡。三道硬约束：代码算数LLM不碰计算器、LLM不碰原始行、无证据不输出。五种降级全跑通——宁可少说不可错说。右下角：这是AI原生做法——AI进核心分析链路，不是给旧流程加聊天插件。
